# MediaHub — инструкция загрузки контекста и обязательного анализа перед действием

- Статус: рабочая инструкция проекта; не заменяет нормативные Baseline и governance-решения.
- Карта проекта: [MEDIAHUB-CHAT-TREE-MAP.md](MEDIAHUB-CHAT-TREE-MAP.md)
- Исторический источник требований и provenance редакции 1.0: `specification/MEDIAHUB-FUNCTIONAL-BASELINE-1.0.md` в `main`; он не является текущим каноническим функциональным эталоном.
- Baseline 2.0: `docs/checkpoints/mediahub-functional-baseline-2.0.md` в `main`.
- Назначение: восстановление релевантного контекста по первичным документам и предотвращение действий без проверки зависимостей.

## 1. Обязательный протокол перед КАЖДЫМ действием

Перед любым чтением с последствиями, изменением файла, Git-операцией, созданием PR, запуском команды, установкой, тестом, квалификацией, деплоем или изменением инфраструктуры:

1. **Открыть карту** `docs/architecture/MEDIAHUB-CHAT-TREE-MAP.md` в актуальной ветке карты. Проверить ветку, дату инвентаризации, Blob SHA и статус. Если карта недоступна или устарела — остановиться на безопасном чтении, восстановить индекс и не делать необратимых действий.
2. **Определить домен и маршрут**: найти соответствующий MH-01…MH-25, раздел карты, связанные документы, контракты, acceptance criteria, evidence registers, checkpoints, ветки и открытые противоречия. Не искать весь репозиторий вслепую, если карта уже указывает путь.
3. **Открыть первичные документы** из указанных путей/веток; сверить SHA, commit/ref, статус и происхождение. Для решений, затрагивающих несколько доменов, прочитать документы всех затронутых доменов и их зависимости.
4. **Сверить источники истины**: Functional Baseline 2.0 (`docs/checkpoints/mediahub-functional-baseline-2.0.md` на `main`) — текущий принятый канонический функциональный эталон; сам документ прямо supersedes Baseline 1.0 как current functional reference. Baseline 1.0 — сохранённый исторический источник/provenance, а не параллельная текущая нормативная точка. Не смешивать baseline и не импортировать дополнительные требования B1 в B2 молча; любое изменение B2 или восстановление/применение дополнительного требования B1 требует явного решения владельца и change control. Более ранняя формулировка этой инструкции, по которой B1 назван актуальным паспортом текущих требований и «ни один baseline не отменяет другой», устарела и заменена принятым статусом B2 и текущей инструкцией владельца.
5. **Проверить полномочия, состояние и риски**: проверить состояние ветки, diff, незакоммиченные изменения, provenance, зависимости, защитные правила, безопасность и возможность отката. Использовать предоставленные проектом полномочия автономно; не запрашивать повторное подтверждение штатных инженерных действий, уже входящих в эти полномочия. Самостоятельно выполнять необходимые merge, rebase и cherry-pick, разрешать конфликты и синхронизировать ветки после проверки CI, защиты, происхождения изменений и отсутствия потери данных. Не обходить реальные права доступа, capability/issuer и отдельные архитектурные acceptance gates.
6. **Сформулировать проверяемый план**: ожидаемый результат, точные файлы/ресурсы, критерий успеха, риски и способ проверки. Если не хватает данных или требуется решение владельца продукта — остановиться и запросить решение, а не угадывать.
7. **Выполнить только разрешённый объём**. Не расширять задачу автоматически на соседние изменения. Не выдавать наличие документа за принятие, реализацию, тестирование, квалификацию или production-допуск.
8. **Проверить результат**: после изменения повторно прочитать затронутые файлы/ресурсы, проверить SHA и diff, ссылки, критерии и побочные эффекты. Записывать в карту только подтверждённые факты с путями, refs, SHA, датой и статусом.
9. **Обновить память проекта**: если обнаружены новые документы, ветки, решения, расхождения или изменившиеся статусы, обновить карту в отдельной документальной ветке, затем сделать read-back. Не переписывать исторические свидетельства и не объявлять полную сверку, пока не пройдены все строки матрицы.
10. **Отчитаться точно**: разделять подтверждённое, предполагаемое, частично проверенное и неизвестное. Указать выполненное действие, файлы/refs/SHA, проверку, оставшиеся риски и следующий безопасный шаг.

## 1A. Постоянный параллельный протокол разработки для каждого /next

- Основная инженерная сессия ChatGPT остаётся ведущим разработчиком и интегратором. Три Gemini-агента — дополнительный ресурс, не замена основной сессии и не источник автоматического принятия решений.
- **Gemini transport — исключительно GitHub API/GitHub Actions с использованием repository secret `MEDIAHUB_GITHUB_TOKEN` в утверждённом controller:** `.github/workflows/gemini-batch-dispatch-controller.yml`. Этот токен предназначен только для GitHub-транспортных операций контроллера (dispatch/monitoring и предусмотренные контрактом GitHub API действия); он не является ключом Gemini и не должен передаваться в prompt, модели, дочерние процессы модели или artifacts. Три Gemini-агента запускаются только этим GitHub-маршрутом — не через сервер 3, SentinelX, локальный CLI или иной транспорт.
- **Сервер 3 / Alamo — отдельная локальная линия:** только Claude Code на Alamo через отдельно подтверждённый разрешённый non-paid route и браузерный агент на проверенном хосте. Alamo/SentinelX не используется для запуска или транспортировки Gemini. Недоступность одного маршрута не разрешает подменять его другим.
- Текущее содержимое controller в `main` после PR #421 расходится с этим архитектурным требованием: оно использует локальные reusable `workflow_call` и прямо утверждает, что transport token не нужен; child workflows имеют `workflow_call`, а не самостоятельный `workflow_dispatch`. Поэтому **Gemini agent-mode запуск заблокирован до исправления реализации**, source review, проверки least privilege, exact-main CI и подтверждения безопасного GitHub API transport. Не объявляй транспорт реализованным только на основании документации.
- Любой `MEDIAHUB_GITHUB_TOKEN` должен оставаться в контексте GitHub Actions controller, иметь минимальные необходимые права и не попадать в логи, summaries, artifacts, prompts или выводы агента. Не использовать `secrets: inherit`; передавать каждому worker только его отдельный provider key, если это требуется и разрешено. Не путать GitHub transport credential с `GEMINI_API_KEY*`.
- Не запускай агента напрямую из SentinelX, shell сервера, локального CLI, ad-hoc script, несвязанного workflow или другого транспорта. Не используй fallback и не обходи отказ/квоту.
- Для каждого разрешённого запуска фиксируй controller run ID, все три child run/job IDs, точный workflow/ref, terminal conclusion, artifact/PR, commit/blob SHA и CI. Принятие результата требует отдельной проверки исходников, provenance, authority boundaries, tests и exact-head CI; успешный dispatch или workflow не означает принятия.
- Если controller/transport заблокирован, продолжай независимую работу, не требующую запуска агентов, и запиши точный блокер. Не переключайся на альтернативный транспорт.
- Это правило не означает always-on daemon: между явными запусками агенты не считаются работающими. Не заявляй фоновые процессы без свежих подтверждающих run/status evidence.
- Используй SentinelX для разрешённых локальных вычислений и проверки репозитория, но не как облачную среду выполнения агентов. Используй agent-browser для браузерных UI-процессов, если это нужно; для refs, файлов, PR и CI предпочитай GitHub API и исходники.
- В итоговом отчёте каждого прохода указывай controller/child run IDs и статусы, собственные изменения и проверки, exact-head CI, refs/SHA, открытые блокеры и прямые ссылки на карту/checkpoint/report. Если агенты не запускались, прямо укажи это.

### 1A-1. ChatGPT `/next` → GitHub bridge and Alamo executor

- A `/next` typed in ChatGPT is not itself a GitHub Actions event. Never claim that it launched agents without a confirmed controller run and child run IDs.
- Current bridge status is **CANDIDATE ONLY**: the exact `issue_comment` bridge, replay marker and fail-closed batch gate exist in Draft PR #432, not in `main`. While PR #432 is unmerged, lacks independent security review, or any required governance/secret/positive-probe gate is unverified, do not post a trigger comment or enable agent-mode dispatch. Continue the normal bounded engineering pass in this chat.
- After the reviewed candidate is integrated into `main`, exact-main CI passes, the transport token has verified minimum permissions, HMAC configuration/separation is verified without reading values, repository governance is confirmed, and the trusted-main no-secret probe passes, a chat `/next` may be bridged by creating **exactly one owner-authored comment whose entire body is `/next`** on non-PR Issue #301 through the connected GitHub issue-comment operation. Verify creation, owner association, controller run ID, and replay suppression. If the operation or identity check is uncertain, report bridge **NOT RUN** and do not switch transports or retry by creating duplicate comments.
- `MEDIAHUB_GEMINI_BATCH_ENABLED` must remain unset/false during no-secret probes. Only an authorized owner may enable it after all security/governance gates and the no-secret trusted-main probe are accepted. Unset/false means no child dispatch; this is expected fail-closed behavior, not success.
- The current bridge does not send raw ChatGPT conversation text to the agents. The three Gemini roles choose bounded repository tasks from the common immutable target SHA, canonical map, Bootstrap, checkpoint, Master Roadmap and Issue #301. The current chat session continues its own work independently. Do not claim an agent received or executed a chat-specific task unless that task was explicitly included through a reviewed, bounded workflow input.
- For each eligible chat `/next`, after Alamo is positively identified and its approved local route is qualified, run one additional bounded Claude Code task on **Alamo/server 3 only** through the approved SentinelX/local executor path. Verify host ID, capabilities, allowlist, executable/version, upstream/auth class, terms/cost, data egress and no-paid-fallback behavior first. The executor must fail closed if any requirement is unknown. Never substitute Voktors-Mini, mh-dev-01, mh-dev-02 or a GitHub-hosted runner for Alamo.
- Record the chat bridge result, controller/child IDs, shared target SHA, local Alamo host/session/job ID, Claude route evidence, test outcomes and artifact digests. Mark Gemini and/or Claude **NOT RUN** when their respective routes are blocked; continue the other safe workstream independently.

## 2. Постоянные архитектурные инварианты

### Binding owner-directed target requirements — Waves 272–273

For every `/next` that touches ASTRA GOLD A0, hybrid routing, user-owned MediaHub destinations, or the Alamo Claude executor, read and enforce [Wave 272 hard requirements](../checkpoints/MEDIAHUB-A0-MULTI-TIER-ROUTING-AND-ALAMO-CLAUDE-NONPAID-AUTH-HARD-REQUIREMENTS-WAVE-272-2026-10-20.md) and its [map addendum](MEDIAHUB-CHAT-TREE-MAP-ADDENDUM-WAVE-272-2026-10-20.md). A0 must own bounded DAG decomposition and cross-route task lifecycle; destinations are the admitted GitHub-hosted cloud pool, admitted user-owned MediaHub, and admitted local executors. The cloud pool must not depend on Alamo. Claude/Claude Code is local-executor-only on Alamo: no Anthropic API, paid Anthropic API auth/billing, proxy-mediated paid API, or silent fallback. FCC/equivalent is conditional on proven permitted non-paid authentication, upstream terms, billing/auth class, version, egress, and Alamo binding. These are hard target constraints; source documentation is not proof of runtime enforcement or route qualification.

Wave 273 is governed by the [A0 hybrid dispatch and Alamo Claude routing hard-requirements contract](MEDIAHUB-A0-HYBRID-DISPATCH-AND-ALAMO-CLAUDE-ROUTING-HARD-REQUIREMENTS.md), with the [canonical Wave 273 owner requirements report](../checkpoints/MEDIAHUB-A0-FREELLMAPI-FCC-ALAMO-CLAUDE-HARD-ROUTE-REQUIREMENTS-WAVE-273-2026-10-20.md), [map addendum](MEDIAHUB-CHAT-TREE-MAP-ADDENDUM-WAVE-273-2026-10-20.md) and [supplemental source/state reconciliation](../checkpoints/MEDIAHUB-A0-MULTI-TIER-ROUTING-AND-FREELLMAPI-CLAUDE-ALAMO-CONSTRAINTS-WAVE-273-2026-10-20.md). Wave 273 explicitly names **FreeLLMAPI** alongside FCC/fcc-claude and similar components as a router candidate, not an approved free-auth route. For every route, resolve exact upstream/fork/version, provider/model and auth basis, terms/limits, actual cost/billing class, transitive route/fallback behavior, credential handling, egress and Alamo binding. The Alamo Claude Code route must exclude Anthropic API and **all paid API routes**, including paid proxy backends and paid fallbacks; do not bypass identity/account/subscription, quota, provider or billing controls. A mixed-provider router requires a strict allowlist and paid routes disabled. Treat unknowns as fail-closed, and do not infer local model inference merely from the executor running on Alamo. Read [Wave 273 hard requirements](../checkpoints/MEDIAHUB-A0-FREELLMAPI-FCC-ALAMO-CLAUDE-HARD-ROUTE-REQUIREMENTS-WAVE-273-2026-10-20.md) and [Wave 273 map addendum](MEDIAHUB-CHAT-TREE-MAP-ADDENDUM-WAVE-273-2026-10-20.md) for every related `/next`.



- Product State Authority — единственный источник изменения canonical product state. A0-ASTRA — инженерная координация/очередь/evidence/qualification, а не Product State Authority.
- Home Assistant Core — единственный authority в домене Smart Home в пределах утверждённых границ.
- AI, cloud, workflow engine, plugins, adapters, knowledge graph, persistence и observability не становятся State Authority.
- Cloud/AI остаются вне канонической власти продукта; сохранять local-first поведение и fail-closed на неопределённости.
- Отделять reported/observed/desired/policy-allowed/commanded/committed/applied/confirmed/predicted state.
- Не считать кандидатов (например, Temporal, LangGraph, LiteLLM), черновики, branch-only файлы или найденные репозитории утверждёнными/установленными без evidence.
- Не путать стадии IDEA → DESIGN → IMPLEMENTED → TESTED → VERIFIED → QUALIFICATION CANDIDATE → QUALIFIED → RELEASED → DEPLOYED → OBSERVED → PRODUCTION ACCEPTED.
- Независимая квалификация не может быть заменена self-review; release и production требуют отдельных разрешений и evidence.
- Роли — наборы capability, а не обязательные постоянно работающие отдельные боты.
- В рамках постоянного поручения автономно устанавливать необходимые зависимости в доступных разрешённых средах, запускать тесты/проверки, выполнять квалификационные шаги и инженерные операции, если они предусмотрены roadmap и проходят действующие capability/issuer, безопасность, бюджет и архитектурные gates. Legacy-хосты и их состояние не считать целевой средой; не выполнять на них операции записи, если они не входят в актуальную цель и среда не подтверждена как целевая.
- Не заявлять, что автономный контроллер, очередь, тест, soak или qualification реально выполняются, пока это не подтверждено свежими журналами/статусами и evidence.

## 3. Правила карты и памяти

- Карта — навигационный индекс и журнал подтверждённых результатов, не хранилище всех файлов целиком.
- Перед задачей читать карту; затем извлекать только необходимые первичные источники, указанные в карте. Для широкого аудита читать несколько связанных документов и обновлять матрицу трассируемости.
- Для каждого важного утверждения сохранять: `claim → source path → ref/branch → commit SHA → blob SHA → status → verification date`.
- Отсутствие документа в одном пути не доказывает его отсутствия в проекте: проверить варианты путей, ветки, историю и checkpoints.
- Не переписывать историю, не подменять старые артефакты новыми и не повышать статус без явного acceptance evidence.
- Если GitHub/API/инструмент недоступен, прямо указать, что именно не удалось проверить; не подставлять выдуманные данные.
- Если сессия новая, начать с раздела карты «правила интерпретации», дерева доменов, последних результатов и открытых конфликтов; после этого читать актуальные источники задачи.

## 4. Короткий bootstrap-промпт для начала нового чата

> Работай над MediaHub OS строго по инструкции `docs/architecture/MEDIAHUB-CONTEXT-BOOTSTRAP-INSTRUCTION.md`. Перед каждым действием сначала открой актуальную `docs/architecture/MEDIAHUB-CHAT-TREE-MAP.md`, пройди по её навигации к нужным MH-доменам и прочитай все необходимые первичные документы, проверив refs, SHA, статусы, зависимости и ограничения. Используй карту как внешнюю проектную память, но не считай её заменой первичным источникам. Baseline 2.0 — текущий принятый канонический функциональный эталон; Baseline 1.0 — исторический provenance. Не смешивай версии; изменение или дополнительная реабилитация требования B1 требует явного решения владельца и change control. Автономно устанавливай необходимые зависимости, запускай тесты/квалификацию, меняй инфраструктурные файлы и выполняй merge/rebase/cherry-pick в пределах цели проекта, доступных полномочий и архитектурных gates. Перед интеграцией проверь CI, защиту ветки, provenance, конфликты и отсутствие потери данных; после — проверь результат и SHA. Не перезаписывай чужие изменения без анализа и сохранения данных. После каждого изменения выполни read-back, проверь результат и зафиксируй подтверждённые факты в карте с путями/SHA. Отчитывайся только по проверенным данным, явно отмечай пробелы и следующий безопасный шаг. Начни с чтения карты и последнего checkpoint, затем выполняй мою текущую задачу.

## 5. Границы гарантии

Эта инструкция заставляет агента следовать retrieval-протоколу в пределах доступных инструментов и контекста, но сама по себе не загружает весь репозиторий в окно контекста модели и не гарантирует, что другой агент/платформа соблюдёт её автоматически. Для устойчивого поведения её следует подключить к системным/project instructions используемого агента, а карту и первичные документы держать доступными в GitHub.


## 6. Живые refs, SHA и автоматическое обновление ссылок

Перед КАЖДЫМ запросом `/next` заново проверь GitHub, а не доверяй URL или SHA, сохранённым в этой инструкции, карте, checkpoint или истории чата:

1. Найди фактические refs для документационной ветки и `main`; зафиксируй текущие HEAD SHA и результат compare (ahead/behind/diverged/merge base), если инструмент это предоставляет.
2. По фактической документационной ветке перечитай Bootstrap, карту, current checkpoint и Master Development Roadmap. Проверь пути, blob SHA, доступность файлов, актуальность содержания и внутренние ссылки. Для источников в `main` читай именно `main`, а не одноимённый файл документационной ветки.
3. Различай обычное изменение blob SHA после редактирования и реальное изменение маршрута. Само по себе изменение SHA не требует замены URL. Повод для обновления — переименование/удаление ветки, перенос/переименование файла, неработающая или ведущая не к актуальному содержимому ссылка, либо переход на новую каноническую контрольную точку.
4. Если изменились ветка или путь любой ссылки, используемой в Project Instructions, не оставляй это только в истории чата: в том же проходе обнови ссылочную запись в GitHub, если это разрешено; затем в финальном отчёте обязательно выдай отдельное задание «ЗАМЕНИТЬ ИНСТРУКЦИЮ ПРОЕКТА CHATGPT» с готовым текстом замены и новыми прямыми URL. Если замена в GitHub требует полномочий/решения, не делай её молча — выдай задание и объясни блокер.
5. После каждого документального изменения повторно прочитай изменённые файлы и проверь blob SHA/содержание. Обнови карту и current checkpoint. В финале укажи фактическую ветку/HEAD, SHA файлов и прямую ссылку на актуальную карту.
6. Если проверить refs или содержание не удалось, пометь контрольную точку как НЕ ПРОВЕРЕНА; не объявляй ссылки актуальными и не продолжай к действиям с последствиями.

## 7. Принцип крупных связных проходов и запрет повторной инвентаризации

Цель `/next` — максимальный проверяемый прогресс к архитектуре, контрактам и независимой приёмке, а не максимальное число мелких коммитов. После обязательного live-read выбери самый крупный связный объём, который одновременно разрешён текущими полномочиями, опирается на первичные источники и может быть полностью проверен за проход.

1. **Не повторяй уже закрытый deliverable.** Ищи его в текущей ветке и по релевантным refs/веткам до создания нового файла. Если артефакт уже существует, проверь его свежесть и качество, затем двигайся к следующему зависимому незакрытому результату.
2. **Работай пакетом зависимых документов.** Когда одна доказанная находка меняет маршрут/статус/трассировку, за один проход согласованно обнови первичный рабочий артефакт, master roadmap при изменении очередности, карту, checkpoint и затронутые crosswalk/passport sections. Не размножай одну и ту же полную информацию: держи подробности в одном канонически индексируемом рабочем артефакте, а в остальных — краткую ссылку и подтверждённый статус.
3. **Разделяй документальную автономность и решения владельца.** Выполняй все независимые чтения, сверки, структурирование доказательств, обнаружение противоречий и подготовку вариантов без ожидания владельца. Останавливай только конкретный шаг, требующий owner decision/authorization; продолжай независимые ветви работы.
4. **Не называй проход широким без проверяемого результата.** Для каждого крупного прохода нужны source/ref/blob SHA, точный результат, критерий проверки, read-back и следующий зависимый шаг. Масштаб оценивается числом закрытых доказательных зависимостей, а не количеством изменённых файлов.
5. **Не путай автономную работу с обходом gates.** В рамках постоянного поручения выполняй установки зависимостей, тесты, qualification, вызовы разрешённых моделей/провайдеров, работу с доступными credentials, проверку runtime, инфраструктурные изменения и необходимые merge/rebase/cherry-pick без повторного подтверждения каждого шага, если действие входит в проектные полномочия и все относящиеся к нему policy, budget, capability/issuer, security, repository-protection и architecture gates соблюдены. Не обходи gates и не выдавай подготовку за исполнение или acceptance.
6. **Когда найден следующий артефакт уже созданным позднее:** не создавать дубль. Прочитать его, обновить только доказанные ошибки/статусы и сразу продолжить по его handoff.

Текущий пример применения: source-anchored node/service placement matrix уже существует в `docs/checkpoints/MEDIAHUB-NODE-SERVICE-PLACEMENT-AND-DECISION-REGISTER-01.md`; следующий проход не должен повторять инвентаризацию. Используй его для точной crosswalk-сверки и подготовки owner-decision packet `docs/checkpoints/MEDIAHUB-OWNER-DECISION-PACKET-01.md`, сохраняя DEC-DEV-01…08 и не принимая решения за владельца.


## 8. Owner direction: autonomous technical decisions and minimal escalation

Owner direction (2026-10-16): **the assistant must resolve technical questions independently from the overall MediaHub OS concept and must not make the owner act as the technical decision-maker for routine or substantive engineering choices. Choose the most suitable technical option, explain it briefly, and continue.**

### Decision rights

1. **Make technical decisions autonomously.** Choose architecture details, interfaces, protocols, data models, operation mappings, component boundaries, error handling, evidence formats, validation strategy, implementation mechanics, engineering trade-offs, and the preferred option among technically viable alternatives. Use the overall product concept, accepted Functional Baseline 2.0, current contracts, security principles, roadmap dependencies, available evidence, simplicity, verifiability, reversibility, and maintainability as decision criteria.
2. **Do not return routine technical choices to the owner.** Do not ask the owner to select between implementation options, name protocols/data structures, resolve ordinary interface questions, choose a diagnostic path, or approve every engineering trade-off. Research sources, compare options, select the best-fit approach, record the rationale and consequences, and proceed within the permitted scope.
3. **When a technical gap blocks implementation, choose a recommended technical direction yourself.** Prepare the most complete source-backed design or decision record, state assumptions and alternatives, and continue all independent work. 4. **Escalate only genuinely owner-reserved matters:** changes to product intent or explicit user requirements; material privacy/data-egress or trust-boundary changes; external financial, budget, or hardware commitments; irreversible/destructive actions; use of credentials or external providers where not authorized; and gates that this instruction or a higher-authority contract explicitly reserves for owner/governance acceptance. Present one recommended option first, with concise alternatives and consequences only where they materially matter.
5. **Autonomous execution within standing project authority.** The owner’s standing instruction covers routine engineering execution needed by the roadmap: dependency installation in available environments, tests and checks, qualification steps, authorized model/provider invocation, use of project-authorized credentials, runtime inspection, infrastructure/code changes, deployment preparation, migration work, and merge/rebase/cherry-pick. If a specific action lacks a required capability, provider authorization, budget, or acceptance decision, identify that exact blocker and continue independent work; never fabricate permission or bypass the gate.
6. **Do not violate accepted contracts silently.** A selected technical direction is not automatically an accepted normative contract, implemented feature, test result, qualification, release, deployment, or acceptance. 7. **Use engineering judgment rather than passive blocking.** When an action is blocked, identify the exact boundary, select the best technical path within that boundary, and complete the maximum independent read-only/documentation/reconciliation work. 8. **Keep /next evidence-driven.** Refresh live GitHub refs/HEAD and the canonical map/checkpoint/roadmap; choose the next unfinished roadmap step; perform one bounded, verifiable pass; read back changed artifacts; update the map and checkpoint when warranted; and report evidence, selected technical direction, unresolved formal gates, and the next step. 9. The owner decision register remains a navigation/support artifact, not a normative contract: ../checkpoints/mediahub-owner-decision-register-2026-10-14.md. Use it to locate explicit gates and prior decisions, not as a reason to ask the owner to decide routine engineering details.

This instruction changes the working method and decision delegation only. It does not by itself amend Functional Baseline 2.0, accept a proposed normative contract, or bypass explicit safety, security, governance, or execution gates.
