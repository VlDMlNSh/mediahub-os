# Mac Pro Desktop — Developer App Specification

**Status:** Proposed capability; implementation and macOS verification pending.  
**Architecture authority:** Subordinate to `architecture/ASTRA-GOLD-REFERENCE-ARCHITECTURE.md`, `architecture/ASTRA-GOLD-GOVERNANCE-CONTRACT.yaml`, and accepted component decisions. This specification does not change Astra Gold's canonical production lanes or grant a new executor admission.

## Goal

Provide a first-class **Mac Pro Desktop** workspace inside the developer application so an operator can identify the paired Mac, see its health, open a remote desktop session, inspect authorized task logs/artifacts, and explicitly control the machine when needed.

“Desktop” means an actual remote desktop stream from a paired Mac host, not a simulated screenshot or a terminal panel presented as a desktop.

## Main screen

### Header / connection state
- Friendly device label (default: Mac Pro; configurable).
- Paired / offline / connecting / connected / stale-heartbeat / revoked states.
- macOS version, hardware architecture, agent version, last heartbeat.
- Current session owner, session start time, and read-only / control-enabled badge.
- Reconnect and Disconnect actions; Revoke device available to authorized administrators.

### Desktop canvas
- Actual live remote desktop stream from the paired Mac.
- Fit-to-window and native-resolution modes.
- Keyboard/mouse input disabled by default.
- An explicit “Enable control” action requires authorization and creates an auditable control session.
- Persistent visible “REMOTE CONTROL ACTIVE” banner while input control is enabled.
- Immediate “Stop control” action, separate from “Disconnect”.
- If the stream is stale or disconnected, input is disabled automatically.

### Side panels
- **Health:** CPU, memory pressure, disk capacity, uptime, network and agent health.
- **Terminal:** separate authenticated shell session, not embedded invisibly into the desktop session; commands and outputs logged according to policy.
- **Tasks:** jobs assigned to this device, current lease, status, cancellation state, and links to run evidence.
- **Artifacts:** logs, screenshots, test results and reports generated by authorized jobs.
- **Access history:** recent pair, connect, control-enable, control-disable, revoke and task events.

## Architecture and boundaries

1. The developer app communicates with the MediaHub control plane; it must not connect directly to arbitrary host ports.
2. A paired workstation agent advertises capabilities and health, but does not gain authority to change canonical Astra state or bypass admission gates.
3. Desktop transport is an adapter. Select and qualify the concrete implementation after testing security, macOS support, latency, codec behavior, accessibility, licensing, and failure recovery.
4. The app must clearly distinguish the live desktop from the shell/terminal, and from CI or a simulated test environment.
5. Control plane remains the authority for access policy and session lifecycle. The desktop transport does not become a source of task/domain state.
6. Existing production lane assignments remain governed by the canonical Astra Gold reference architecture. Naming a device “Mac Pro” or pairing it does not automatically promote it into a permanent production lane.

## Pairing and access lifecycle

- Pairing starts from an authenticated operator action.
- Device displays or receives a short-lived pairing challenge; challenge expires and is single-use.
- Operator verifies device identity and intended environment before accepting.
- Device credentials are scoped, stored securely, rotatable and revocable.
- Session tokens are short-lived; no long-lived bearer tokens in URLs or logs.
- Authorization is checked on connection and again before enabling input control.
- Default mode is view-only. Input control requires an explicit per-session action.
- Disconnect, timeout, revocation, or stale heartbeat disables input and invalidates session tokens.
- Every privileged action records actor, device, timestamp, authorization decision, and outcome.
- Remote desktop access must not silently capture unrelated personal content; define capture/retention policy and indicate recording when enabled.

## Failure behavior

| Failure | Required behavior |
|---|---|
| Mac offline | Show offline and last heartbeat; no fake live view; queue device-specific jobs or mark blocked by policy |
| Agent crash | Mark stale after configured threshold; stop accepting new jobs; recover after authenticated heartbeat |
| Desktop transport failure | Show disconnected; disable input; preserve task state independently |
| Session expires | Re-authenticate; do not reuse expired credentials |
| Operator loses authorization | Immediately revoke control and terminate/disable session |
| Network loss during control | Input channel fails closed; host-side session timeout disables input |
| Mac restarts | Re-register/heartbeat, report new boot identity, require session reconnect |
| Disk/CPU pressure | Surface alert; do not silently kill user processes |
| Control-plane unavailable | No new control session; current session follows bounded fail-closed policy |

## Acceptance criteria

- [ ] A real paired macOS host appears in the developer app with accurate OS, architecture and heartbeat.
- [ ] Offline/stale states are distinguishable from an active stream.
- [ ] Desktop view displays a real host desktop; no mocked stream can be reported as live.
- [ ] View-only is the default.
- [ ] Enabling input requires explicit permission and is auditable.
- [ ] Disconnect, token expiry, and revocation stop input control.
- [ ] Task state and desktop state remain separate.
- [ ] Session and audit artifacts contain no passwords, raw tokens, or cookies.
- [ ] Reconnect, network-loss and host-restart tests pass on real macOS.
- [ ] Transport choice and license/security review are recorded as an architecture decision.

## Hardware-arrival checklist

1. Record Mac model, chip architecture, macOS version, memory and disk.
2. Create a dedicated OS account for the workstation agent; enable FileVault and OS updates.
3. Install and verify the signed workstation agent using the documented bootstrap.
4. Pair device with a one-time challenge; verify revocation.
5. Run read-only telemetry tests before enabling any shell or desktop control.
6. Run the desktop test suite in view-only mode.
7. Verify control-enable banner, input stop, token expiry and network-loss fail-closed behavior.
8. Run Linux/macOS portability and Astra integration tests against a pinned commit.
9. Attach logs, screenshots, environment metadata and checksums to the evidence ledger.
10. Admit the device to any production lane only through the existing canonical qualification and human-approval gates.
